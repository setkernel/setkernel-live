  1. Someone describes what they want, in plain words, in an issue. No template and no meeting.
  2. Before any code, the work gets a charter: the phases it goes through and the acceptance examples that say when it is done.
  3. An engineer picks it up and works in a pull request, in small commits that each say why.
  4. Done means proven: tests run, screenshots are attached, and every check passes on the exact commit.
  5. A second model reviews the change and looks only for what would block it. Every blocker is fixed before the merge.
  6. A person reads the evidence and merges. Nothing reaches production without a human sign-off.
  7. After the deploy, a smoke check confirms the new version is the one running. If it fails, the deploy rolls back by itself.
  1. The idea: put the approved Day design on live.setkernel.com, in place of the old page.
  2. Two phases. First a clickable prototype, chosen from screenshots (its pull request); then this build, held to the criteria.
  3. Lyra built it on the day the design was picked.
  4. The screenshots are in the repo, taken by a script at fixed sizes (see them).
  5. The automated reviewer found one blocker; it was fixed in the next commit. Then Rigel, a second engineer, approved.
  6. Merged by a person, after reading the evidence.
  7. The deploy waited until live.setkernel.com reported the merged commit, then checked every route (the deploy run). It is the page above.
